# 提示词与上下文的关系分析

> 提示词不但没死，反而因为上下文变大而更加重要——但它的角色发生了根本性转变。
> 日期：2026-05-13

---

## 一、核心论点

**提示词和上下文不是竞争关系，是编译器和数据的关系。**

```
提示词 = 编译器（定义如何处理信息）
上下文 = 数据（提供要处理的信息）

编译器不会因为数据变多而失去价值——恰好相反，数据越多，越需要编译器来组织和约束。
```

---

## 二、证据一：上下文窗口变大反而放大了"注意力稀释"问题

2024-2025 研究反复验证同一个现象：

| 研究 | 发现 |
|------|------|
| Lost in the Middle (Liu et al.) | 长上下文中，中间位置的信息被严重忽略 |
| Needle in a Haystack | 虽然能找到，但精确提取和多跳推理显著下降 |
| Anthropic 内部研究 | 超长上下文（100K+）中，指令遵循能力退化——模型开始"忘记"system prompt 的要求 |

**这意味着什么？** 上下文塞了 200K token 的知识库内容，但模型可能只对开头和结尾的信息有有效关注。如果没有一个强有力的提示词在开头锚定"你要怎么处理这些信息"，中间那 150K token 几乎等于白给。

---

## 三、证据二：前沿 Agent 框架的实践指向同一个方向

没有一个成熟框架在"弱化"提示词，反而都在做**结构化提示词工程**。

| 框架 | 做法 | 本质 |
|------|------|------|
| CrewAI | 角色(Role) + 目标(Goal) + 背景(Backstory) | 结构性提示词 |
| LangGraph | System prompt + State schema | 提示词定义行为边界，状态承载上下文 |
| Anthropic | Tool use system prompt + tool definitions | 提示词定义"如何用工具" |
| MetaGPT | SOP 编码为 Role 提示词 | 流程固化在提示词中 |

CrewAI 的 `backstory` 字段本质上是"角色化的行为约束"，和原始系统提示词是同一类东西，只是做了结构化封装。

## 四、证据三：上下文和提示词解决的是不同层级的问题

```
┌─────────────────────────────────────────────────────┐
│                   提示词做什么                        │
│                                                     │
│  1. 行为约束    "你必须先问过敏史再开处方"          │
│  2. 流程控制    "先检索，再生成，最后自检"          │
│  3. 质量标准    "诊断建议必须标注证据等级Ⅰ-Ⅴ"      │
│  4. 角色人格    "你是一个审慎的临床医生"            │
│  5. 输出格式    "请用 SOAP 格式输出"                │
│  6. 安全边界    "永远不要建议患者停用处方药"        │
│                                                     │
├─────────────────────────────────────────────────────┤
│                   上下文做什么                        │
│                                                     │
│  1. 事实知识    "该患者的肌酐值是 1.8 mg/dL"        │
│  2. 参考素材    "2024版咳嗽诊疗指南摘录..."         │
│  3. 对话历史    "上一轮你说头痛，现在说胸痛"        │
│  4. 工具结果    "药物相互作用查询返回了3条结果"     │
│  5. 用户背景    "用户是基层全科医生，非专科"        │
│  6. 错题本提醒  "上次类似任务遗漏了过敏史询问"      │
│                                                     │
├─────────────────────────────────────────────────────┤
│                                                     │
│  提示词 = 如何思考 + 什么是好的                      │
│  上下文 = 思考什么 + 当前状态                        │
│                                                     │
│  两者作用不同，不可能互相替代。                     │
└─────────────────────────────────────────────────────┘
```

## 五、证据四：大上下文反而需要更精确的提示词

以 PDCA 多智能体架构为例。一期只有 RAG（小上下文），提示词可以简单。但到三期，上下文里同时塞入了：

- 对话历史（可能有几十轮）
- RAG 检索结果（可能十几条文档片段）
- 错题本匹配记录（top 3）
- 工具调用返回（多个 API 结果）
- 合规规则清单
- 领域模板

**这时候如果没有一个强提示词来组织优先级，模型就懵了——不知道在这些海量上下文里，哪个是最重要的、哪个只是参考。**

有效的做法是在提示词中明确定义优先级：

```
"在处理当前任务时，请按以下优先级使用上下文信息：
  1. 错题本记录 > 2. 合规规则 > 3. RAG检索结果 > 4. 对话历史
  如果 RAG 结果与合规规则冲突，永远以合规规则为准。
  如果错题本提示了某个历史错误模式，请优先对照检查。"
```

这是纯粹的提示词能力——上下文再多，也无法自己定义优先级。

## 六、结论：新的关系模型

```
旧模型 (2023):
  提示词 = 全部指令
  上下文 = 很少

过渡模型 (2024-2025):
  提示词 = 全部指令
  上下文 = RAG结果 + 工具输出 + 对话历史
  → 提示词负担很重，上下文也很重

正确模型 (2025-2026):
  提示词 = 元指令 + 优先级框架 + 行为约束 + 质量标准
  上下文 = 运行时数据（通过 MCP/工具/RAG 动态注入）
  记忆 = 历史经验（通过错题本/向量库注入）

  三者各司其职：
  ┌──────────┐
  │ 提示词    │ ← "怎么想" "什么是好" "边界在哪"
  ├──────────┤
  │ 上下文    │ ← "有什么信息可用" "当前状态是什么"
  ├──────────┤
  │ 记忆      │ ← "过去发生了什么" "什么模式值得注意"
  └──────────┘
```

## 七、对 PDCA 智能体架构的启示

六个横向智能体每一个都需要精心设计的 system prompt：

- **路由 Agent 提示词**：定义意图分类规则 + 紧急度评估标准 + 分发决策逻辑
- **内容生成 Agent 提示词**：定义模板选择规则 + 引用格式标准 + 语言风格约束
- **合规校验 Agent 提示词**：定义硬/软/建议三级规则 + 校验流程 + FAIL 处理策略
- **多角色评审 Agent 提示词**：定义四个评审视角 + 聚合规则 + 升级人工的条件
- **知识检索 Agent 提示词**：定义三层检索策略 + 权威性加权 + 溯源标注格式
- **错题本引擎提示词**：定义入库条件 + 检索匹配阈值 + 引导注入策略

每一个提示词都是该智能体的**行为编译器**。上下文（RAG 结果、工具输出、错题本记录）是编译器处理的数据——数据再多也替代不了编译器的逻辑。

---

## 八、一句话回答

**提示词不会消失，它会从"完整指令"演变为"元指令 + 优先级框架"。上下文越大，越需要一个清晰的元指令来告诉模型在这些信息里怎么取舍。**
