# 医疗数据脱敏与合规操作清单

> 适用场景：从医院 HIS/EMR 提取真实世界数据（RWS），交付给药企或研究机构前，完成去标识化和合规处理。
> 法规依据：《个人信息保护法》《数据安全法》《健康医疗大数据安全管理办法（试行）》、GB/T 35273-2020、HIPAA Safe Harbor（参考）。

---

## 一、前置合规确认（动手前必须过）

| 检查项 | 通过标准 | 不通过时 |
|--------|----------|----------|
| 数据来源授权 | 有明确的医院合作协议 / 科研伦理批件 / 数据处理协议（DPA） | **停。** 无授权即违法，先补协议 |
| 用途范围 | 当前用途在原始授权范围内（科研？商用？） | 商用需额外授权或知情同意 |
| 伦理审批 | 涉及回顾性研究至少要有伦理委员会批件或免审通知 | 没有伦理批件 → 药企合规部不会收 |
| 患者知情同意 | 原始数据采集时有知情同意，或伦理批准了免知情同意（回顾性匿名数据通常可免） | 必须确认，不可跳过 |
| 数据存储安全 | 数据存储在加密介质中，不放在个人电脑明文目录 | 先加密再处理 |
| 传输安全 | 发给第三方使用加密传输（VPN/加密邮件/专用平台），不发微信/普通邮箱 | 违反即数据泄露 |

## 二、直接标识符 —— 必须删除（不可逆删除，不是打码）

以下字段**完全删除**，不留原文、不留映射表（除非你干的是临床研究且有合法留存的知情同意）：

### 患者身份标识
- [ ] 姓名（包括拼音、缩写、曾用名）
- [ ] 身份证号 / 军官证号 / 护照号
- [ ] 医保卡号 / 社保号
- [ ] 住院号 / 门诊号 / 病历号（如果院内唯一且不可逆则可留加密版）
- [ ] 手机号 / 固定电话
- [ ] 电子邮箱
- [ ] 家庭住址（精确到门牌号）
- [ ] 工作单位名称
- [ ] 紧急联系人姓名与电话

### 生物识别与影像
- [ ] 人脸照片（原始）、指纹、声纹、虹膜
- [ ] DICOM 影像中的患者姓名、ID（Header 字段）
- [ ] 病理切片中的患者条码

### 可追溯标识
- [ ] 车牌号、设备序列号
- [ ] 微信 OpenID、支付宝 UserID、APP 设备号
- [ ] 区块链地址、数字证书编号

### 医疗相关唯一号（需变形处理）
- [ ] 处方号、检查号、手术号 —— 保留前 N 位或做加密映射

## 三、准标识符 —— 必须泛化或扰动（K-匿名 ≥ 5）

以下字段**不能直接保留原始值**，需通过泛化、聚合或加噪处理，使任意组合下无法定位到少于 5 个人。

| 字段 | 处理方法 | 示例 |
|------|----------|------|
| 年龄 | 转为年龄段或出生年份 | 原始：57岁 → 处理：55-60 / 1960-1969 |
| 出生日期 | 只保留年份 | 原始：1968-03-15 → 1968 |
| 入院/出院日期 | 转为相对天数（Day 0 = 入院日） | 原始：2015-06-15 → Day 0；出院：Day 7 |
| 死亡日期 | 同上，不能保留绝对日期 | 所有日期偏移 |
| 邮政编码 | 只保留前 3 位 | 原始：100080 → 100 |
| 籍贯 / 户籍地 | 归到省级 | 原始：海淀区 → 北京市 |
| 民族 | 极小民族归为"其他" | 人口 < 0.1% 的民族合并 |
| 职业 | 归为大类 | 原始：Java 工程师 → IT/互联网 |

### K-匿名验证逻辑
1. 取所有准标识符的组合（如 [性别, 年龄区间, 省份, 入院年份]）
2. 统计每个组合下的人数
3. 任何组合人数 < 5 → 需要进一步提高泛化程度
4. 记录被剔除的记录数（信息损失度）

## 四、敏感数据字段 —— 脱敏或加密

以下字段可以保留，但不能以原始形式：

| 数据类型 | 方案 A（不可逆） | 方案 B（可逆，需密钥管理） |
|----------|-----------------|--------------------------|
| 诊断代码（ICD-10）| 保留前 3 位 | AES-256 加密 |
| 检验数值 | 加随机噪声（±5%）或分组 | 保留，但删除极值标识 |
| 用药信息（药品名、剂量）| 标准化为通用名，去掉生产批号 | 加密批号和厂家 |
| 医院名称 | 编码代替（Site_01, Site_02） | AES 加密，密钥单独存 |
| 医生 ID | 加密映射为研究 ID | 同上 |
| 费用金额 | 按年度 CPI 调整后四舍五入到百元 | 保留原始值需合规批准 |
| 自由文本（病历、医嘱备注）| 正则扫描删除人名、地名、电话后保留 | 全文脱敏引擎处理 |

### 自由文本脱敏专项
- [ ] 用正则匹配并删除/替换：姓名（包括"患者""病人"后的名字）、电话号码、身份证号、地址、机构名
- [ ] 对罕见病名称做泛化（某些罕见病 + 地区 = 可识别）
- [ ] 人工抽查 100 条确认无漏网

## 五、技术实施核查清单

### 抽取阶段
- [ ] 抽取 SQL 中 WHERE 条件不包含直接标识符（避免日志泄露）
- [ ] 抽取过程记录操作日志（谁、何时、抽取了什么字段、多少条）

### 脱敏处理阶段
- [ ] 使用独立于生产环境的脱敏服务器
- [ ] 脱敏工具不放原始数据和脱敏后数据在同一目录
- [ ] 脱敏映射表（如有）单独加密存储，不与数据包一起交付
- [ ] 每一批数据生成脱敏处理报告（字段清单 + 处理方法 + 信息损失评估）

### 交付阶段
- [ ] 交付格式：CSV / SAS / 加密 SQLite，不用 Excel（列宽限制可能截断数据）
- [ ] 交付前用自动化脚本扫描一遍，确认无直接标识符残留
- [ ] 传输用加密通道（SFTP / 加密邮件 / 专用数据平台）
- [ ] 交付包附带《数据脱敏声明》（签名、日期、处理人）

## 七、常见踩坑与救命建议

| 坑 | 建议 |
|----|------|
| "我把名字换成 MD5 就行了吧？" | MD5 可被彩虹表反查，不够。用 SHA-256+盐值，或者直接删除 |
| "住院号不重要，留着吧" | 住院号 + 住院日期 + 性别 + 年龄 → 几乎可以确定唯一患者。删。 |
| "数据量大了不会被识别" | K-匿名不看总量，看组合。10 万条数据里"某罕见病+某县+45岁+女"可能只有一个 |
| "给医院内部用不需要脱敏" | 内部用途也分。开发测试环境和科研分析环境的安全级别不同 |
| "签了保密协议就行了" | 保密协议管人，管不了数据泄露后的法律责任。技术脱敏 + 协议双保险 |

## 八、参考标准速查

| 标准 | 核心要求 |
|------|----------|
| GB/T 35273-2020（个人信息安全规范）| 去标识化定义、匿名化 vs 去标识化区分 |
| GB/T 37964-2019（去标识化指南）| 技术方法：掩码、泛化、加噪、置换 |
| HIPAA Safe Harbor | 18 类标识符删除清单 |
| GDPR Article 4(5) | 匿名化定义："不可逆地无法识别" |
| 《个人信息保护法》第 4 条、第 51 条 | 处理必要性 + 安全保护措施 |
| 《数据安全法》第 21 条 | 数据分类分级 |

> **一句话：宁可数据少给 10 个字段，也别给 1 个能定位到人的字段。脱敏后自己拿 10 条去"试试能不能反查到人"——你脱敏的标准不应该是"我觉得够了"，而是"我查不回来"。**
