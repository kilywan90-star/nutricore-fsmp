## 二、六大通用智能体

### 核心洞察：三个领域的同构性

政企、医疗、教育表面差异巨大，但在智能体层面存在深层结构同构：

| 维度 | 政企 | 医疗 | 教育 | 通用抽象 |
|------|------|------|------|---------|
| 权威知识源 | 法律法规、公文规范 | 临床指南、药典 | 课程标准、教材 | **知识库适配层** |
| 内容生产 | 公文撰写、政策解读 | 病历、处方、报告 | 教案、试题、评语 | **结构化内容生成** |
| 质量红线 | 格式合规、法条引用 | 用药安全、诊断依据 | 评分标准、学术诚信 | **合规校验引擎** |
| 多方审查 | 多级审批流程 | 多学科会诊(MDT) | 多维度评估 | **多角色评审** |
| 服务对象 | 群众/企业 | 患者/家属 | 学生/家长 | **服务路由+分级** |
| 风险等级 | 行政责任 | 生命健康 | 成长发展 | **分级管控策略** |

**不是做三套智能体，而是做一套通用智能体内核 + 三个领域的配置适配层。**

### Agent 1：服务路由智能体 (Triage & Router)

**通用职责**：作为用户的第一接触点，完成意图理解、需求分级、任务分发。

| 维度 | 政企 | 医疗 | 教育 |
|------|------|------|------|
| 典型输入 | "我要开办餐饮企业需要什么手续" | "我头痛三天了还发烧" | "孩子数学成绩一直上不去" |
| 分级策略 | 简单咨询→直接回答；复杂审批→启动多Agent | 轻症→健康建议；急重症→立即就医；模糊→追问 | 一般→资源推荐；学业困难→学情分析→个性化方案 |
| 路由目标 | 政策问答/表单生成/人工窗口 | 健康咨询/分诊/紧急提醒 | 学习诊断/内容推荐/教师对接 |
| 安全拦截 | 识别"找关系"等不当诉求 | 识别危及生命症状，绕过正常流程 | 识别心理危机信号，触发紧急干预 |

**关键设计**：路由 Agent 不直接回答领域问题，只做意图分类 + 紧急度评估 + 任务分发。保证完全通用。

### Agent 2：结构化内容生成智能体 (Content Generator)

**通用职责**：根据领域模板和约束，生成符合规范的结构化内容。三个领域中最核心的生产力智能体。

**通用生成流水线**：

```
用户需求 + 上下文
      │
      ▼
┌──────────────┐
│ 模板匹配     │ ← 从领域模板库中选取最佳模板
├──────────────┤
│ 知识检索     │ ← 调用知识检索Agent获取权威素材
├──────────────┤
│ 约束注入     │ ← 调用合规Agent获取该内容类型的规则清单
├──────────────┤
│ 初始生成     │ ← LLM 按模板+素材+约束生成初稿
├──────────────┤
│ 自检修正     │ ← 对照约束清单逐项自检，自动修正明显违规
├──────────────┤
│ 输出+置信度  │ ← 附带逐项约束的通过/存疑标记
└──────────────┘
```

| 维度 | 政企 | 医疗 | 教育 |
|------|------|------|------|
| 内容类型 | 通知公告、请示报告、函、会议纪要、政策解读 | 门诊病历、出院小结、检查报告、处方 | 教案、试题、评语、学情报告 |
| 格式约束 | 《党政机关公文格式》GB/T 9704 | 病历书写基本规范、ICD编码 | 课程标准、学科核心素养框架 |
| 引用要求 | 法律法规条款 + 文号 + 发文机关 | 临床指南版本 + 证据等级(Ⅰ-Ⅴ) + 文献DOI | 课标编号 + 教材版本 + 页码 |
| 语言风格 | 规范严谨、无歧义、适当敬语 | 客观描述、量化指标、避免绝对化 | 适龄语言、正面引导、避免标签化 |

### Agent 3：合规校验智能体 (Compliance Guardian)

**通用职责**：独立于生成流程，对输出内容进行规则化校验，具有一票否决权。整个架构中最关键的安全阀。

**合规校验流程**：

```
待校验内容
      │
      ▼
┌─────────────────┐
│ 规则集加载      │ ← 根据内容类型加载对应的规则清单
├─────────────────┤
│ 逐条校验        │
│ ┌─────────────┐ │
│ │硬规则 → MUST PASS  (违反=拒绝)             │
│ │软规则 → SHOULD PASS (违反=标记提醒)        │
│ │建议规则→ NICE TO HAVE (违反=优化建议)      │
│ └─────────────┘ │
├─────────────────┤
│ 校验报告        │
│ PASS / FAIL / PASS_WITH_WARN                │
└─────────────────┘
```

**三领域规则示例**：

| 规则等级 | 政企 | 医疗 | 教育 |
|---------|------|------|------|
| 硬规则 MUST | 公文必须有发文机关+发文字号+印章 | 处方剂量不得超说明书最大剂量；青霉素必须确认皮试 | 试题不得包含歧视性内容 |
| 软规则 SHOULD | 政策解读建议附带原文链接 | 诊断建议应有鉴别诊断列表 | 评语应先肯定后建议 |
| 建议规则 NICE | 长公文建议有内容摘要 | 医嘱建议标注服药时间 | 教案建议标注预计时长 |

**关键设计**：合规 Agent 必须独立于生成 Agent 运行——不能是同一个 LLM 调用中的"自我审查"，而是一个独立的、拥有不同 system prompt 甚至不同模型的检查节点。

### Agent 4：多角色评审智能体 (Multi-Perspective Reviewer)

**通用职责**：模拟多个利益相关方视角，对内容进行多维度评审，发现单一视角遗漏的问题。

**评审架构**：

```
待评审内容
      │
      ├──→ 角色A (权威视角)    "法规/指南/课标是否符合？"
      ├──→ 角色B (受众视角)    "群众/患者/学生能看懂吗？"
      ├──→ 角色C (相关方视角)  "财务/护理/家长会有什么疑问？"
      └──→ 角色D (反方视角)    "如果结论是错的，最可能错在哪？"
      │
      ▼
┌──────────────┐
│ 评审聚合     │
│ 一致通过 → 放行                              │
│ 部分异议 → 标注分歧点，附多方意见            │
│ 严重分歧 → 触发辩论轮 → 仍分歧则升级人工     │
└──────────────┘
```

| 角色 | 政企 | 医疗 | 教育 |
|------|------|------|------|
| 权威视角 | 法律顾问：法条引用准确 | 资深主任医师：诊断逻辑 | 教研组长：课标符合度 |
| 受众视角 | 办事群众：流程易懂 | 患者/家属：医嘱可执行 | 学生/家长：内容适龄 |
| 相关方视角 | 财务/审计：预算合规 | 药师/护士：药物相互作用 | 心理老师：评语影响 |
| 反方视角 | 行政复议模拟：薄弱点 | 鉴别诊断：替代可能 | 认知偏差：错误认知 |

### Agent 5：知识检索智能体 (Knowledge Retriever)

**通用职责**：从领域知识库中检索权威信息，提供可溯源的引用。

**三层检索架构**：

```
用户查询
      │
      ▼
┌─────────────────┐
│ 查询理解+改写   │ ← 将模糊查询改写为精确检索语句
├─────────────────┤
│ 层级检索        │
│ L1: 结构化库    │ ← 法律法规/临床指南/课程标准（精确匹配）
│ L2: 案例库      │ ← 历史案例/典型病例/优秀教案（语义检索）
│ L3: 经验库      │ ← 错题本/专家经验/隐性知识（图检索）
├─────────────────┤
│ 结果排序+去重   │ ← 权威性加权 + 时效性衰减 + 来源标识
├─────────────────┤
│ 溯源标注        │ ← 每条引用带来源+版本+时间戳
└─────────────────┘
```

| 维度 | 政企 | 医疗 | 教育 |
|------|------|------|------|
| L1 结构化库 | 法律法规数据库、政策文件库 | 临床诊疗指南、药典、ICD编码库 | 国家课程标准、教材知识图谱 |
| L2 案例库 | 历史审批案例、典型答复 | 典型病例库、会诊记录 | 优秀教案库、学生错题模式库 |
| L3 经验库 | 审批要点经验、常见驳回原因 | 罕见病经验、用药经验 | 教学策略经验、常见误解 |
| 权威性权重 | 国家级 > 省级 > 市级 | 指南 > 专家共识 > 个案 | 课标 > 教材 > 教辅 |
| 时效性衰减 | 法律法规以生效日期为准 | 指南以版本为准 | 课标以发布年份为准 |

**关键设计**：检索 Agent 的输出永远是"带来源的信息"，不是"我认为的答案"。确保可溯源性。

### Agent 6：错题本学习引擎 (Error Book & Learning Engine)

**通用职责**：PDCA 闭环的 Act 阶段，整个架构最核心的差异化竞争力。

**四层记录模型**：

```
L4: 洞察层 — 跨任务、跨领域的可泛化策略规则
    "医疗+教育+政企共用: 当用户描述模糊时，先追问澄清再生成"
    "政企特有: 涉及多部门时，必须标注牵头部门和配合部门"
    "医疗特有: 任何用药建议必须附带剂量和禁忌"

L3: 模式层 — 同一错误类型在同类任务中的反复出现模式
    "公文核稿中，文种使用错误占驳回原因的37%"
    "医疗问诊中，漏问过敏史是最常见的严重失误"
    "教育评估中，评语过于笼统是学生满意度最低的场景"

L2: 修正策略层 — 针对每一个错误模式的具体修正策略
    "文种错误 → 在生成时注入文种选择决策树提示"
    "过敏史遗漏 → 在问诊流程中增加强制过敏史确认节点"
    "评语笼统 → 要求每条评语包含具体事例+改进建议"

L1: 基础记录层 — 每条失败/不满意任务的完整轨迹
    任务签名 + 执行路径 + 输出 + 评价 + 用户反馈 + 修正结果
```

**触发入库的三种途径**：

| 途径 | 触发条件 | 适用场景 |
|------|---------|---------|
| 自动触发 | 合规Agent判定 FAIL；或质量评分 < 0.5 | 硬规则违反、事实错误 |
| 用户标记 | 用户主动反馈"不满意"或"不准确" | 体验不佳、信息不全 |
| 周期性挖掘 | 每日/每周对 PASS_WITH_WARN 内容回溯 | 发现系统性偏差 |

**检索注入的三种模式**：

| 模式 | 机制 | 时机 |
|------|------|------|
| 主动拦截 | 任务签名匹配到 L2/L3 → 生成前注入到 system prompt | Router 分配任务时 |
| 实时比对 | 输出与 L1 相似失败案例比对，偏差超阈值 → 提醒 | 生成后、合规校验前 |
| 复盘报告 | 任务完成后自动生成"相似任务执行对比报告" | 最终输出时附带 |

## 三、领域适配机制

核心原则：**智能体的逻辑流程完全通用，领域差异通过外置配置层注入。**

```
┌────────────────────────────────────────────┐
│         通用智能体执行引擎                  │
│  (相同的状态图、相同的节点顺序)             │
├────────────────────────────────────────────┤
│         领域适配配置层                       │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐   │
│  │ 角色人格 │ │ 知识库   │ │ 规则集   │   │
│  │ Persona  │ │ KB Config│ │ Ruleset  │   │
│  └──────────┘ └──────────┘ └──────────┘   │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐   │
│  │ 模板库   │ │ 输出Schema│ │ 风险矩阵 │   │
│  │ Templates│ │ Schema   │ │ Risk Map │   │
│  └──────────┘ └──────────┘ └──────────┘   │
```

## 六、可行性评估

### 技术成熟度审计

| 能力 | 成熟度 | 当前真实水平 | 落地风险 |
|------|--------|-------------|---------|
| 意图分类+路由 | 成熟 | GPT-4o/Claude 分类准确率 >95% | 低 |
| RAG 知识检索 | 成熟 | 主流方案，无数生产案例 | 低（但知识库建设是苦活） |
| 模板化内容生成 | 成熟 | 结构化输出 + JSON Schema 约束 | 低 |
| 规则化合规校验 | 成熟 | 规则引擎（非LLM）+ 正则/JSON Schema 校验 | 低 |
| 单步自我反思 | 基本可用 | "检查你刚才的输出"确实能发现一些错误 | 中（也会引入新错误） |
| 多Agent协作 | 基本可用 | LangGraph/CrewAI 有生产案例，但质量波动大 | 中高 |
| LLM做合规审查 | 有条件可用 | 审查另一个LLM输出，准确率70-85% | 高（两个LLM可能同时犯错） |
| 多角色辩论 | 实验阶段 | 论文效果好，生产环境成本高、收益不稳定 | 高 |
| 自动错误模式提炼 | 实验阶段 | ReasoningBank/SAMULE是论文，非产品 | 很高 |
| RL驱动策略优化 | 研究阶段 | Mem-α等训练成本极高，泛化未验证 | 很高 |

**架构中 60% 的能力已经可用，30% 需要谨慎降级，10% 当前不可行需要替换方案。**

### 三个必须做的减法

#### 减法一：多角色辩论 → 规则化交叉检查

不使用四个LLM辩论（成本5-8倍，延迟+40-60秒，可能放大错误），改用：

```
1 个结构化的交叉检查清单（Checklist Engine）
+ 1 个 LLM 按清单逐项审查

检查清单示例（医疗场景）：
  □ 诊断是否有鉴别诊断列表？           ← 规则检查，不需LLM
  □ 用药建议是否有剂量和禁忌？         ← 规则检查，不需LLM
  □ 是否标注了证据等级？               ← 规则检查，不需LLM
  □ 是否有危险信号提醒？               ← 规则检查，不需LLM
  □ 语言是否适合患者理解？             ← LLM检查（仅此一项）
```

**核心原则：能用规则解决的不用 LLM，LLM 只做规则做不到的语义判断。**

#### 减法二：四层错题本 → 两层可运转 + 两层渐进建设

```
第一期只建两层：

L1: 完整记录层 ← 立即可建
  - 每条任务的完整轨迹 + 用户反馈
  - 纯存储，不需要 AI 处理
  - 价值：出了问题可以回溯，人工分析根因

L2: 精确匹配层 ← 立即可建
  - 基于关键字段的精确检索
  - "同一类任务 + 同一类错误" → 返回上次的修正方案
  - 不做语义泛化，只做精确召回
  - 价值：避免完全相同的错误重复发生

L3/L4 渐进建设：
  - 积攒 1000+ 条 L1 记录后 → 人工标注 100 条 → 训练分类器
  - 积攒 5000+ 条后 → 尝试半自动模式聚类
  - L4 跨任务洞察 → 人工编写 + 定期更新，不追求自动生成
```

**核心原则：先做"精确匹配的记忆"，再做"语义泛化的智能"。前者已能解决 60% 的重复错误。**

#### 减法三：合规 Agent 独立 LLM → 规则引擎 + LLM 混合

```
合规引擎 = 规则引擎 (80%) + LLM语义检查 (20%)

规则引擎处理：
  - 必填字段检查、数值范围检查、格式检查、关键词检查
  → 100% 准确，0 LLM调用

LLM 语义检查处理：
  - 语言风格是否得体、逻辑一致性、模糊规则判断
  → 这是LLM真正有价值的地方

混合架构：
  规则引擎先跑 → 硬规则 FAIL 直接打回（不浪费 LLM 调用）
                → 硬规则 PASS 后，LLM 只做语义检查
```

### 分期落地路线

#### 第一期：单Agent + 知识库（1-2个月，可上线）

交付物：知识检索Agent (RAG)、模板化内容生成、规则化校验

```
用户提问 → RAG检索 → LLM生成 → 规则校验 → 输出
```

不做：多Agent协作、多角色辩论、自动错题本、LLM做合规审查

可落地行业：
- 政企：政策问答机器人（贵州疾控模式，已验证）
- 医疗：结构化报告生成（影像报告、病历摘要）
- 教育：学情反馈生成、试题自动批改

#### 第二期：双Agent + 基础错题本（2-3个月）

新增：服务路由Agent、L1错题本（完整记录）、L2错题本（精确匹配）

```
用户提问 → 路由Agent(分类+分级+错题本检索)
        → 低复杂度 → 直接生成
        → 高复杂度 → 生成 + 规则校验 + 人工确认
```

- 政企：公文初稿生成 + 人工核稿（错题本记录每次核稿修改）
- 医疗：辅助问诊 + 鉴别诊断建议（错题本记录误诊模式）
- 教育：个性化学习诊断 + 资源推荐（错题本记录错误学习路径）

#### 第三期：多Agent协作 + LLM合规（3-4个月）

新增：内容生成Agent（升级）、LLM合规检查（混合）、简单多角色检查（Checklist模式）、错题本半自动提炼

- 政企：多部门联合发文协作生成
- 医疗：多学科辅助会诊建议
- 教育：多学科交叉评估

#### 第四期：持续学习 + 主动进化（长期迭代）

新增：L3/L4错题本、Prompt自动优化、跨任务经验迁移

不做：RL自动策略优化、全自动跨领域知识迁移、端到端自进化

### 真实成本估算

以日活 1000 用户、日均 5000 次对话为例：

| 期数 | 日均LLM调用 | 月均API成本 | 其他成本 |
|------|-----------|-----------|---------|
| 一期 | 5000 | ~$450 | 知识库建设：2人月 |
| 二期 | 10000 | ~$1200 | 人工标注：持续 |
| 三期 | 20000 | ~$3000 | 运维+审核：1人 |
| 四期 | 25000 | ~$3750 | 专家标注：持续 |

**API 成本是最小的开销。真正的大头是：**
1. 领域知识库建设（法律法规录入、临床指南结构化、课程标准数字化）
2. 规则引擎的规则编写和维护（需要领域专家参与）
3. 错题本的人工审核和标注（保证质量的关键）
4. 现有系统的对接集成（政务系统、HIS、LMS 等）

### 最大风险

1. **知识库是最大瓶颈**：法律法规、临床指南、课程标准持续更新。知识库维护成本远超模型调用成本。过期信息比没有信息更危险。

2. **医疗和教育场景的责任边界模糊**：
   - 医疗：输出永远定位为"辅助参考"而非"诊断决策"，强制标注证据等级，高风险场景强制人工确认
   - 教育：AI 评价不直接向学生/家长输出，先给教师确认，教师有修改权和否决权
   - 政企：公文生成后必须经过人工核稿流程，AI 不做最终审批

3. **政企场景的私有化部署**：本地可部署的开源模型（Qwen、DeepSeek等）在多步推理和指令遵循方面与闭源模型仍有差距。一期设计就要考虑模型无关性。

## 八、总结

**这是一个正确的方向，但要走"先简后繁、先规则后智能、先记录后学习"的渐进路线。**

一套不做减法的"完美架构"恰好是无法落地的架构。

核心原则：
- 能用规则解决的不用 LLM
- 先做精确匹配的记忆，再做语义泛化的智能
- 每个阶段都有独立价值，不完全依赖下一阶段
- 最推荐起步行业：政企政策问答

## 十、企业落地优先级与路线

### 分批落地建议

不是所有 12 类一起上，按 ROI 和成熟度分三批：

#### 第一批：立即可做（3-6 个月见效）

| 业务域 | 理由 | 参考案例 |
|--------|------|---------|
| 客户服务 Agent | ROI 最清晰，技术最成熟 | Typewise、联想乐享、Tata Steel TDA |
| 知识管理 Agent | 内部提效，Day 1 可建知识库 | 蓝凌×中交建(满意度95%) |
| 法务合同审查 Agent | 有成熟可复制的模式 | 国家能源集团、ContractPodAi、Ironclad |

#### 第二批：6-12 个月（需要领域数据积累）

| 业务域 | 理由 | 参考案例 |
|--------|------|---------|
| 营销内容生成 Agent | 需要品牌素材库和风格数据 | 联想乐享(创收18.9亿) |
| 财务费控/报表 Agent | 需要对接现有财务系统 | Oracle Financials、来也科技 |
| 人力资源 Agent | 简历筛选 + 员工服务需求明确 | Workday Illuminate、Tata Steel |

#### 第三批：12 个月+（需要错题本数据支撑）

| 业务域 | 理由 | 参考案例 |
|--------|------|---------|
| 供应链预测 Agent | 需要大量历史运营数据 | Tata Steel(地缘政治+价格预测) |
| 采购招投标 Agent | 需要行业法规库+历史标的 | 讯飞"招采首席官"、金蝉 |
| 战略决策辅助 Agent | 需要跨领域数据聚合 | Oracle Analytics、FII SAGE |
| 跨域端到端自动化 | 需要前两批 Agent 稳定运行的数据 | — |

### 关键成功因素

1. **不是做一个"超级 Agent"，而是一个 Agent 矩阵**——每个 Agent 有明确的能力边界和职责范围。Tata Steel 的 300 个 Agent 不是一个大模型，而是 300 个专业化的小型智能体。

2. **Agent 的权限边界必须清晰**——财务 Agent 可以生成凭证但不能审批，销售 Agent 可以建议折扣但不能突破底线。每一类 Agent 都需要定义"可自主执行"和"必须人工确认"的边界。

3. **数据基础决定 Agent 上限**——没有结构化的合同库，合同审查 Agent 就是无源之水；没有历史招投标数据，围串标检测 Agent 就没有训练素材。Agent 的价值 = 模型能力 × 数据质量。

4. **先从"辅助人"开始，再逐步走向"替代人"**——来也科技、讯飞、联想的所有成功案例都遵循这个路径。Agent 先做副驾驶，跑顺了再放开自动化权限。

5. **Agent 不是绕过企业系统，而是嵌入企业系统的"手和眼"**——Oracle 的做法是 Agent 直接在 Fusion Cloud 内运行，共享同一套 RBAC 和权限体系。这是正确路径。
